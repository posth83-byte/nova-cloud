# JARVIS Trading

Automated crypto spot-trading project with a multi-specialist AI research team and deterministic risk/execution controls.

## Objective
The user may fund a separate account with up to 200 SEK of their own money. Once the user explicitly enables live mode after all validation gates pass, the bot is intended to buy and sell spot crypto automatically. The objective is positive net returns after fees and slippage; profit is never guaranteed. Report losses and drawdowns honestly.

Profits may remain in the trading account and be automatically reinvested. The 500 SEK limit applies to the user's external funding/deposits, not to account growth generated by trading profits. No automatic deposits or transfers are permitted. Reinvestment does not relax risk limits or authorize larger risk per trade.

## Team and architecture
- Market Scanner: public spot market data and movement/volume detection.
- Technical Analyst: explainable indicators and signals.
- Opportunity Hunter: ranks setups but cannot bypass risk controls.
- Strategy Developer: reproducible backtests and strategy comparisons.
- Risk Manager: deterministic limits and position sizing.
- Final Review: records approve/reject decisions.
- Execution Engine: validates balances, precision, minimums, fees, spread, data freshness and duplicate orders before submitting spot orders.
- Portfolio Monitor: reconciles balances, orders, fills, exits and P&L.

AI is advisory. Deterministic code has final authority and can reject any proposal.

## Initial scope
- Kraken spot market data first; verify provider authorization/availability in Sweden/EEA before funding.
- BTC/EUR and ETH/EUR only initially, subject to current availability and minimum order size.
- Maximum external funding for this initial test: 200 SEK. Profits may grow account equity above 500 SEK through automatic reinvestment.
- No automatic top-ups, deposits, transfers or withdrawals.
- Spot only: no margin, leverage, futures, shorting, borrowing or staking.
- Full automatic buy/sell is the intended live mode after separate user activation.
- Live execution remains DISABLED during development. No exchange credentials are present.
- Report realized/unrealized P&L net of fees, spread and estimated slippage, and distinguish deposited capital from profit.

## Implemented paper-trading layer
- `paper_engine.py` is an offline, deterministic, long-only spot paper broker.
- It supports one open position, allowlisted symbols, stop-based sizing, automatic stop-loss monitoring, a 1% maximum risk budget per trade and a 2% daily drawdown entry stop.
- Entry/exit fees and configurable slippage are included in simulated fills and realized P&L.
- Paper state is persisted atomically to a local JSON file in file mode. `supabase_state.py` adds server-side persistence to the RLS-protected `jarvis_trading_state` table for scheduled runs; only the Supabase service role can access it.
- Realized profit remains in the cash balance and can be reinvested; external funding is tracked separately.
- The broker has no exchange client, no API credentials and no live-order path.
- `paper_strategy.py` adds a transparent EMA-trend/RSI/volume baseline with automatic stop-loss and trend exits; it is for paper evaluation only, not a proven profitable strategy.
- `paper_runner.py` runs one complete cycle using public Kraken market data.
- `paper_daemon.py` continuously polls public data, processes each completed hourly candle only once, and persists the portfolio. It is paper-only and stops on Ctrl+C.
- `backtest.py` evaluates historical candles with fees/slippage, closed-candle signals and next-candle-open entries to reduce look-ahead bias.
- `download_history.py` downloads public Kraken candles without credentials for offline backtesting.
- `dashboard.html` is a read-only portfolio/backtest panel served by the NOVA Cloud app at `/trading`. It imports exported JSON files locally in the browser; it cannot place orders or access exchange credentials.
- `paper_config.json` contains conservative defaults. Pass `--starting-cash` in the quote currency only after applying a current SEK/EUR conversion; do not assume 500 SEK equals 500 EUR.

Example: download 30 days of hourly BTC/EUR candles and backtest with an example EUR balance:

```bash
python trading/download_history.py --symbol BTC/EUR --timeframe 1h --days 30 --output trading/history.json
python trading/backtest.py --input trading/history.json --starting-cash 470 --output trading/backtest-result.json
```

For consecutive out-of-sample windows (at least three folds; each fold is flattened at its boundary):

```bash
python trading/backtest.py --input trading/history.json --starting-cash 470 --walk-forward --test-window 168 --output trading/walk-forward-result.json
```

The walk-forward report compounds the paper balance across non-overlapping test windows and compares it with a fee/slippage-adjusted buy-and-hold benchmark. It uses prior candles only as indicator warmup; it does not train or optimize the strategy. Inspect fold-by-fold consistency, not just the aggregate return.

Example continuous paper watcher (example EUR balance only):

```bash
python trading/paper_daemon.py --starting-cash 470 --state-path trading/paper-state.json
```

The daemon is not deployed or running in the background yet. The example balance is not a conversion of the user's 500 SEK budget.

Open the dashboard after the app branch is deployed at `/trading`. Import the JSON portfolio state or a daemon snapshot, plus a backtest result. Files stay in the browser and are not uploaded.

Run tests from the repository root:

```bash
python -m pip install -r trading/requirements.txt
python -m unittest discover -s trading -p "test_*.py" -v
```

## Initial simulation risk policy
- One open position at a time.
- Maximum planned loss per trade: 1% of current equity.
- Daily stop: 2% drawdown from start-of-day equity; block new entries after breach.
- Every entry needs a defined exit/stop rule.
- No averaging down, martingale, leverage or shorts.
- Enforce a 5 EUR minimum simulated order notional for Kraken EUR markets; skip smaller setups rather than rounding up.
- Skip trades if fees + spread + slippage make expected edge uneconomic.
- Check exchange minimum, precision, quote balance and fees before each order.
- Never increase size just to meet an exchange minimum.
- Kill switch blocks new orders; cancellation/closing behavior must be separately tested.
- User can revoke trading permission at any time.
- Automatically reinvest available realized profits only while all risk, balance and order checks pass.

At 200 SEK, 1% risk is only 2 SEK. Minimum orders and round-trip fees may make many strategies impractical. Skip uneconomic trades rather than forcing activity.

## Live activation gates
- Explicit user approval for the chosen exchange and live automated trading.
- Verify provider authorization/availability for Sweden/EEA.
- API key limited to read and spot trading; withdrawals, transfers, margin and futures disabled.
- Keys stored only as encrypted deployment secrets; never committed or printed.
- Tests for risk limits, sizing, fees, minimum order, precision, partial fills, duplicate orders, stale data, retries, reconciliation and kill switch.
- Backtests include fees/slippage and out-of-sample periods.
- At least 8 weeks forward paper trading on live market data with reviewed net metrics.
- A tiny live pilot requires separate approval and strict capital cap.

## Deployment
Do not assume a sleeping/free web service can run an always-on worker. Use local Docker for development, then select an always-on worker after costs and reliability are understood.
